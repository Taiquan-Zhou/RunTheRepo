The seven final-epoch failures are:

authorized.

## 3. Goal

Close the M7.5 release gap without changing the product architecture or frozen
semantics. A release candidate exists only when one unified production HEAD,
using the unchanged frozen cohort and SHAs, achieves all of:

- autonomous success `>=7/10`;
- meaningful regression-passing convergence `>=5/10`;
- exact failed stop reason `100%`;
- final-epoch cleanup `100%` and empty final inventory;
- exact SHA verification `100%`;
- no host fallback;
- every result produced by the same production HEAD.

### Approach decision

Three approaches were considered:

1. **Evidence-gated shared compatibility recovery (selected).** Diagnose one
   cross-repository failure domain at a time, permit a production change only
   after a real target and trusted fixture prove the same bounded cause, then
   validate all release claims on one unchanged HEAD. This costs more diagnostic
   runs but preserves the product and safety contracts.
2. **Blanket resource and timeout expansion (rejected).** Increasing disk,
   readiness, and command timeouts together could raise the pass count without
   proving which limit was necessary. It would hide hangs and workload-specific
   failures and would contradict the calibrated resource evidence.
3. **Repository-specific compatibility branches (rejected).** Matching names,
   URLs, SHAs, images, or services would be fast for the frozen cohort but would
   turn the benchmark into hard-coded exceptions and violate MVP scope.

The selected approach is deliberately conditional: a failed evidence gate
produces an `unsupported` or workload-limitation ruling, not speculative code.

## 4. Non-goals and frozen boundaries

- Do not start M8 or reopen M0-M7.4.
- Do not replace, reorder, or remove repositories or commit SHAs.
- Do not add repository-name, URL, SHA, service-name, or image-name branches.
- Do not execute target Compose on the host.
- Do not expose host Docker sockets, credentials, SSH material, or model keys.
- Do not execute README commands. README and repository content remain untrusted
  data.
- Do not change `README.md` during diagnosis, compatibility, or convergence
  work. It remains unchanged unless the final unified release gate passes.
- Do not mutate the source Compose in place. Runtime compatibility changes use
  validated inputs or separate overlays/artifacts.
- Do not change LangGraph orchestration, M5 Engine contracts, M6 checkpoint
  semantics, M7 report/API/CLI semantics, Journey verification, or
  KEEP/ROLLBACK rules without an explicit Owner ruling.
- Do not increase timeouts, retries, memory, or disk merely until a run passes.
- Do not weaken a verifier, denominator, cleanup rule, or coverage requirement.
- Do not claim PID protection or global safety/least privilege.

## 5. Delivery model

Work is strictly serial because the failure domains share provider, graph, and
trial files. Each implementation task follows:

1. Controller checks spec, task dependency, Git status, and fresh baseline.
2. Controller records `BASE_SHA` in an isolated worktree.
3. Fresh implementer receives one bounded task brief and follows RED -> GREEN ->
   REFACTOR.
4. Implementer runs scoped tests, commits, self-reviews, and writes a report.
5. A different reviewer checks spec compliance, correctness, security, tests,
   cleanup, and scope from the exact diff.
6. Controller inspects the diff and fresh evidence; Critical/Important findings
   require a bounded fix and scoped re-review.
7. Controller runs applicable full gates before accepting the task.

Every real-repository diagnostic is serial, exact-SHA, `docker-sbx` only,
diagnostic-only until a new unified cohort is frozen, and append-only in the
evidence ledger. No full ten-repository cohort runs during root-cause work.

### RG0.2 - Sandbox preflight

Run only read-only health probes until the daemon state is known. Do not invoke
commands with implicit daemon-start behavior as health probes. Record:

- `sbx.exe`/SBX client and server version;
- `sbx diagnose` result;
- authentication status as SET/UNSET or pass/fail, never credential values;
- initial inventory;
- available state-volume capacity;
- `REPOTRIAL_MODEL_API_KEY` as SET/UNSET only;
- selected endpoint class and model name without secrets.

Exit gate: SBX diagnose passes, initial inventory is empty, and the calibrated
trusted-client network route works. PID remains disclosed as unsupported.

## 7. Stage 1: Autonomous-success closure

Each subsection begins as systematic debugging. A production fix is allowed
only after its stated evidence gate passes. If the gate fails, record the
result and move to the next evidence-supported domain without speculative code.

### RG1 - Docker-data capacity cluster

Scope: Uptime Kuma and n8n-hosting; NetBox may be used only as historical
corroboration because its final epoch failed for readiness, not disk.

Commit `9931834` already calibrated the allocation formula. At `2048 MiB` it
assigns root `1 MiB`, Docker data `1919 MiB`, and workspace `128 MiB`; that total
was sufficient for Umami and did not authorize a larger shared default.

Diagnostic sequence:

1. Retain the current `2048 MiB` policy evidence as control; do not rerun it
   merely to recreate known ENOSPC.
2. Run exact-SHA targeted probes serially at total budgets `4096 MiB`, then
   `8192 MiB` only if `4096 MiB` still produces Docker-data ENOSPC.
3. Change only `SandboxPolicy.disk_mb`; retain CPU `1`, memory `1024 MiB`,
   whole-trial `900 s`, network denies, model configuration, and commit SHA.
4. Persist requested root/docker/workspace allocations, guest `df -Pm`, image
   pull/extract result, Boot evidence, lifecycle JSONL, duration, and inventory.
5. Stop at the smallest total that removes ENOSPC for both repositories, or at
   `8192 MiB` if no shared bounded result exists.

Implementation entry gate: both repositories independently cross image
pull/extraction without ENOSPC at a common bounded total. Passing Boot is not
required to prove capacity, and later failures remain failures.

If the gate passes, the bounded TDD task changes only the shared CLI/API default
policy and tests. Candidate files:

- `src/repotrial/cli.py`
- `src/repotrial/api/app.py`
- `tests/unit/test_cli.py`
- `tests/unit/api/test_app.py`
- `tests/unit/sandbox/test_docker_sbx_commands.py` only if the existing pure
  allocation contract needs a test for the calibrated total

The existing `calculate_disk_allocation()` formula is already calibrated and
must not be changed unless the new evidence specifically disproves it. RED must
show both entry points still construct the old `2048 MiB` default. GREEN uses
the smallest common proven total. Explicit user-supplied `disk_mb`, exact hard
sum, official environment variables, insufficient-budget fail-closed behavior,
cleanup, and provider interfaces remain unchanged.

Target verification: rerun both exact-SHA probes on the reviewed HEAD. Required
result is no Docker-data ENOSPC, exact SHA, exact stop reason if failed, cleanup
PASS, and empty inventory for both.

### RG2 - Deterministic startup-input materialization

Scope: Linkding's documented `.env.sample -> .env` requirement. This task does
not execute README prose and does not inject host environment values.

Diagnostic entry gate:

- prove the selected Compose file references variables whose required source is
  an absent service-level `env_file`, rather than only unresolved interpolation;
- prove a bounded repository-local template contains the required keys;
- prove values are local non-production defaults or can be replaced with the
  existing deterministic synthetic value policy;
- prove the target path is absent and its resolved parent remains inside the
  verified guest clone;
- add a trusted fixture reproducing the same Compose/template shape.

Proposed implementation boundary after the gate:

- add a small typed parser/materializer in `src/repotrial/trial/` rather than
  extending the model prompt;
- accept only regular, non-linked, bounded UTF-8 files with recognized names;
- parse key/value data, never shell syntax or command substitution;
- reject control keys (`COMPOSE_*`, `DOCKER_*`, `LD_*`, `DYLD_*`, `PATH`,
  `HOME`, Python control variables) and values requiring host secrets;
- reuse `GraphContext.env` and `GraphState.recovery_env` for the effective Boot
  values; do not add or change checkpoint fields;
- because `SandboxProvider.copy()` is guest-to-host only, create the missing
  runtime file only inside the disposable guest and only after provider clone
  verification, using `SandboxProvider.exec()` through one explicit,
  deterministic adapter;
- persist the adapter body, argv category, input source hash, output hash, target
  relative path, accepted key names, result, and any rejection reason as audit
  artifacts; never persist values;
- require confinement to the verified guest clone, an absent non-linked target,
  exclusive creation, mode `0600`, bounded content, and post-write hash
  verification before Boot;
- never create or overwrite the host source repository's `.env` file. The guest
  runtime file is ephemeral and disappears with sandbox destruction.

Candidate files:

- Create: `src/repotrial/trial/startup_inputs.py`
- Create: `tests/unit/trial/test_startup_inputs.py`
- Modify: `src/repotrial/agent/graph.py`
- Modify: `tests/unit/agent/test_graph.py`
- Add a dedicated trusted fixture under `tests/fixtures/`

TDD must cover valid templates, symlinks/reparse points, size and entry bounds,
duplicates, invalid UTF-8, shell syntax, forbidden control keys, secret-looking
values, guest path escape, pre-existing targets, exclusive creation, file mode,
post-write hashes, deterministic persistence, checkpoint replay with the existing
state schema, and collision-safe artifacts. The real Linkding verification must
use its frozen SHA and require Boot to progress past the former missing-input
failure; any later failure is retained.

This task changes startup input handling, not RecoveryAction, Journey, mutation,
Compose source semantics, or the `SandboxProvider` public interface. A fixed
shell adapter is permitted only when it is code-owned, non-LLM-generated,
argv-invoked, persisted as an audit artifact, and proven to treat all target data
as inert input. If safe guest-local materialization requires executing repository
setup instructions, adding host-to-guest `copy()`, or changing a frozen provider
interface, stop and request an Owner ruling.

### RG3 - Guest-loopback publication compatibility

Scope: changedetection.io plus a trusted fixture that binds a published
container port to guest loopback.

First determine the failing boundary with three probes:

1. service reachability from inside its target container;
2. service reachability from the sandbox guest using the Compose-published port;
3. service reachability through `SandboxProvider.publish_port()`.

Persist only addresses, ports, status, and bounded errors. The entry gate passes
only when the application and guest-loopback path work but the provider-published
path fails for the same port.

Preferred implementation after the gate is a separate generated compatibility
overlay that normalizes a loopback-only host binding to a sandbox-reachable
binding for trial execution. It must:

- be generated from parsed Compose structure, never string replacement;
- preserve the container port and protocol;
- change only recognized loopback host-IP bindings;
- be stored and hashed as an audit artifact;
- leave source Compose unchanged;
- run only inside the disposable sandbox;
- fail closed for ranges, ambiguous mappings, host networking, unsupported tags,
  or collisions.

Candidate files:

- Create: `src/repotrial/compose/compatibility.py`
- Create: `tests/unit/compose/test_compatibility.py`
- `src/repotrial/agent/graph.py`
- `src/repotrial/hardening/engine.py` only to consume the same effective trial
  Compose, not to change KEEP/ROLLBACK semantics
- `tests/unit/agent/test_graph.py`
- `tests/unit/hardening/test_engine.py`

The compatibility artifact is distinct from a hardening mutation: it is selected
before baseline Boot, immutable for the trial, applied identically to baseline,
Journey execution, observation, and every hardening candidate, and never counts
as meaningful convergence. `compose/overlay.py` remains responsible only for the
existing one-service hardening overlay contract.

Because applying an additional trial Compose artifact may affect what the M5
Engine regards as its effective base, the implementation plan requires an
explicit Owner ruling that this compatibility layer may be threaded through the
graph and engine without changing KEEP/ROLLBACK, parent/candidate hashing, or
checkpoint semantics. Without that ruling, RG3 stops after diagnosis and the
trusted-fixture proof.

### RG4 - Wakapi command-timeout diagnosis

Do not increase the timeout first. Persist the exact timed-out argv category,
elapsed time, child start/kill/reap result, bounded stdout/stderr tail, remaining
whole-trial time, and Compose service state after cleanup.

Entry gate: the same trusted operation and a trusted slow fixture exceed the
current per-command limit while remaining inside the whole-trial deadline, and
the child cleanup path is proven. If the target is genuinely hung or cleanup is
unconfirmed, no timeout increase is authorized.

If the gate passes, use a named Boot-operation timeout bounded by the remaining
whole-trial deadline; do not change generic exec timeout semantics. Candidate
files are `src/repotrial/trial/boot.py`, its focused tests, and graph/engine tests
that prove baseline and candidate parity. Exact values come from the measured
successful interval plus a documented fixed margin, capped below `900 s`.

### RG5 - Paperless clone-verification evidence

The current evidence is insufficient for a fix. First rerun the frozen SHA once
on the reviewed baseline and require complete bounded raw status entries,
configuration facts, and truncation metadata.

Entry gate: the retained evidence identifies a deterministic tracked-path or Git
configuration difference and reproduces it with a trusted local Git fixture.
Only then may a TDD task modify `src/repotrial/sandbox/docker_sbx.py` and
`tests/unit/sandbox/test_docker_sbx_commands.py`.

Permitted corrections normalize a proven platform representation while still
requiring exact HEAD, work-tree identity, and clean tracked content. Ignoring
unknown status, untracked content generally, malformed output, or a SHA mismatch
is prohibited.

### RG6 - NetBox dependency-readiness diagnosis

Build a trusted multi-service fixture in which the application observes a
database recovery transition. Capture Compose health state and timestamps across
the existing `--wait --wait-timeout 60` boundary.

Entry gate: both NetBox and the trusted fixture become healthy after the current
60-second readiness window but within a repeatable bounded interval, with no
configuration or data error. If only NetBox reproduces, retain it as a workload
limitation and do not add a repository-specific wait.

If the gate passes, change one shared readiness constant in
`src/repotrial/trial/boot.py`, prove baseline/candidate parity in
`tests/unit/trial/test_boot.py`, `tests/unit/agent/test_graph.py`, and
`tests/unit/hardening/test_engine.py`, and keep the provider command timeout and
whole-trial deadline coherent. Arbitrary retries remain prohibited.

### Stage 1 canary gate

After accepted RG1-RG6 changes are combined on one reviewed HEAD, run the frozen
repositories affected by those accepted changes, serially. These canaries are
diagnostic only: they may justify the cost of a complete cohort, but they are not
release metrics and cannot be combined with historical results from another
HEAD. Continue only if at least four of the seven former failures now satisfy
autonomous-success conditions. If fewer than four recover, do not run a complete
cohort; return to the remaining evidence-supported failure, or record that the
release threshold is not currently achievable without broader product changes.

### Stage 1 candidate-cohort gate

After the affected-repository canary passes, freeze its reviewed production HEAD
and run all ten frozen repositories once, serially, in manifest order. No code,
policy, manifest, model, or environment change is allowed between attempts. This
candidate cohort is the only Stage 1 basis for calculating autonomous success or
selecting repositories for Stage 2.

The gate requires autonomous success `>=7/10`, exact SHA `10/10`, exact stop
reason for every failure, final-epoch cleanup `100%` with empty inventory, and no
host fallback. This is a development gate, not the final release measurement;
later production changes invalidate it and require the final RG10 cohort.

## 8. Stage 2: Meaningful-convergence closure

Stage 2 begins only after the same-HEAD Stage 1 candidate cohort reaches at least
`7/10` autonomous success.
This prevents mutation work from optimizing the three surviving repositories
while most workloads still cannot reach the experiment phase.

### RG7 - Nine-rollback evidence matrix

For every experiment on the successful candidate cohort, persist and classify:

- risk finding and evidence that selected the mutation;
- mutation type, service, parent hash, and candidate hash;
- exact candidate Boot result and failed service;
- full baseline/replay Journey IDs and deterministic verdicts;
- before/after observations used for grounding;
- final KEEP/ROLLBACK/STOP reason;
- cleanup and inventory result.

No production policy changes occur in this task. Exit gate: every rollback has
one exact class: application Boot regression, infrastructure/provider failure,
Journey regression, insufficient observation, or mutation-construction failure.

### RG8 - Ground one mutation class at a time

Select the largest cross-repository rollback class supported by at least two real
repositories or one real repository plus an existing trusted capability fixture.
Create a separate TDD task for that class. Do not batch non-root, capabilities,
read-only/tmpfs, Docker socket, privileged, and network mutations.

The first likely inspection surface is:

- `src/repotrial/hardening/policy.py`
- `src/repotrial/compose/mutations.py`
- `src/repotrial/hardening/engine.py`
- corresponding focused tests and existing eval fixtures

This is not prior authorization to change those files. The RG7 matrix selects the
exact task. Any accepted design must preserve:

- one principal privilege reduction per experiment;
- separate overlay and parent/candidate hashes;
- complete baseline Journey replay;
- deterministic KEEP only after Boot and every required Journey pass;
- ROLLBACK on Boot/Journey regression;
- STOP on unsupported or insufficient evidence;
- no static or LLM-only success decision.

If a minimal add-back is justified, it must be grounded in retained runtime
evidence and represented by an existing typed mutation or an Owner-approved
extension. Never infer required Linux capabilities from log prose alone.

### Stage 2 canary gate

Run hardening canaries only on repositories that succeeded in the same-HEAD
Stage 1 candidate cohort. If RG8 changed production code, rerun those repositories
on the new reviewed HEAD before interpreting their hardening results. The gate
requires meaningful KEEP on at least five frozen repositories, with complete
baseline replay and privilege reduction evidence. The canary is diagnostic and
does not contribute final release metrics. Three consecutive ROLLBACKs remain a
valid stop condition and remain in the denominator.

If fewer than five converge after every evidence-supported mutation task, stop
and report the unmet product gate. Do not weaken `meaningful` or add trivial
`add_tmpfs` KEEP rows.

## 9. Stage 3: Unified release candidate

### RG9 - Freeze and verify one production HEAD

Before real execution:

- all task reviewers approve with no open Critical/Important findings;
- controller reviews the full diff from `b2dc2c2`;
- Linux Ruff, format, mypy, full pytest, and branch coverage `>=85%` pass;
- scoped SBX integration suites pass;
- dependency lock is unchanged unless an accepted task required a dependency;
- manifest byte hash and all ten URLs/SHAs match the frozen cohort;
- SBX diagnose passes and inventory is initially empty;
- the exact model endpoint class/name and code HEAD are frozen;
- no secret value is written to artifacts, logs, tests, or Git.

### RG10 - Final cohort

Run all ten repositories once, serially, in manifest order on the unchanged HEAD.
For each attempt retain exact command, expected/actual SHA, timing, target-workload
boundary, report, Journey set/results, experiments, stop reason, lifecycle,
cleanup, and post-attempt inventory.

No code, manifest, policy, model, or environment change is allowed between the
ten metric-bearing attempts. Any pre-workload infrastructure invalidation follows
the existing frozen replacement-attribution rules and remains append-only.

### RG11 - Release ruling and documentation

Compute metrics mechanically from the frozen evidence. Update
`docs/dev/pilot-report.md`, the relevant append-only evidence document, and
`docs/dev/status.md` in all outcomes.

Update `README.md` to release wording only if every threshold in section 3
passes. Otherwise retain the development-snapshot wording and state precisely
which gates failed. Always retain PID unsupported disclosure, tested-journey /
workload-conditioned language, exact SHA evidence, cleanup facts, and no-host-
fallback facts.

README and final evidence receive an independent documentation/claims review in
addition to code review.

## 10. Per-task verification and reporting contract

Every production task report contains:

- task ID;
- `BASE_SHA` and `HEAD_SHA`;
- changed files;
- root-cause evidence and the single tested hypothesis;
- RED command and expected failure;
- GREEN/scoped commands and results;
- full applicable gates;
- real SBX verification or explicit `unsupported`;
- reviewer findings and disposition;
- known limitations and controller rulings.

Minimum repository gates are:

```text
uv run ruff check .
uv run ruff format --check .
uv run mypy src/repotrial
uv run pytest -q
uv run pytest -q --cov=repotrial --cov-branch --cov-fail-under=85
```

Integration tasks additionally run their focused real-SBX or trusted-fixture
suite. Missing runtime capability is reported as `unsupported`; it is never
reported as passed.

## 11. Stop and escalation rules

Stop the current task before code changes when:

- the evidence entry gate is not met;
- a proposed fix needs a repository-specific branch;
- a frozen public/domain interface must change;
- cleanup cannot be proven;
- target execution would bypass `SandboxProvider`;
- verification would require a production secret;
- the same hypothesis fails three times;
- a fix would weaken Journey, KEEP/ROLLBACK, exact-SHA, stop-reason, cleanup, or
  no-host-fallback semantics.

Escalate the exact evidence and required Owner ruling. Do not broaden scope to
make progress.
