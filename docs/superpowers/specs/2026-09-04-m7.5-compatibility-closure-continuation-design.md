# M7.5 Compatibility Closure Continuation Design

## 1. Status and authority

The Owner approved this continuation design in chat on 2026-09-04 after the
original release-gap loop closed at commit
`8b8ca42fd28b7030c1b6a696d3eb1a0185e7634e`.

This design supersedes only the Task 8 scope ruling
`no broader compatibility work authorized`. It does not rewrite or invalidate
the append-only Pilot ledger, historical attempt roles, stop reasons, cleanup
denominators, or the accepted M0-M7.4 contracts. The earlier
`STAGE1_RECOVERY_GATE_UNMET` result remains a correct historical result for its
evaluated HEAD.

Authority remains:

1. `docs/project/RepoTrial_AI_Agent项目立项文档_v0.1.docx`
2. `docs/superpowers/plans/2026-08-25-repotrial-mvp.md`

The implementation plan produced from this design records its own exact
`IMPLEMENTATION_BASE_SHA`. Production work must descend from that commit and
remain in the existing isolated ext4 worktree unless the worktree safety check
requires a replacement.

## 2. Goal

Produce one reviewed production HEAD that passes the frozen M7.5 release gates:

- autonomous real-repository success at least `7/10`;
- meaningful regression-passing hardening convergence at least `5/10`;
- exact pinned SHA verification `10/10`;
- exact stop reason for every failed repository;
- final-epoch cleanup `100%` and exact empty final sandbox inventory;
- no host fallback;
- one unchanged production HEAD for the final metric-bearing cohort.

The three historical successes, Umami, Listmonk, and Dockge, are mandatory
regression sentinels. A compatibility correction is not accepted if it breaks
one of them or weakens its evidence.

PID hard-bound enforcement remains explicitly `unsupported` under the Owner's
frozen M7.5 ruling. This design neither implements nor claims PID protection.

## 3. Evidence that changes the continuation strategy

The previous loop exposed seven different terminal boundaries rather than one
shared defect:

| Repository | Latest retained boundary |
|---|---|
| Uptime Kuma | Boot and observation passed; `GET /` returned `302` while the Journey expected `200` |
| n8n-hosting | Boot passed; Observer `docker diff` exceeded its 30-second command timeout with 664 seconds of total trial budget remaining |
| Wakapi | Compose build/start crossed 240 seconds and later returned unhealthy after about 333 seconds |
| Paperless-ngx | Boot rejected an absent/default application secret; recovery planning timed out |
| NetBox | migration process was killed and the resulting database schema was incomplete |
| Linkding | the post-fix canary stopped at a pre-workload clone timeout |
| changedetection.io | the target probe stopped during pre-workload intake |

On 2026-09-04 the unchanged production Intake path was probed again in temporary
directories:

- Linkding completed in 10.96 seconds and `clone_and_resolve()` accepted the
  exact requested SHA.
- changedetection.io returned Git exit 128 once after about 78 seconds, then
  completed on a second invocation in 28.14 seconds. The production intake
  rejects a requested full-SHA mismatch.

These results do not retroactively reclassify or replace historical attempts.
They prove only that a fixed Intake timeout increase is not currently justified.
No Intake production change is authorized by this design.

## 4. Approach decision

Three approaches were considered.

### Selected: evidence-gated compatibility funnel

Use diagnostic canaries to expose one exact boundary, implement only a generic
correction with a failing regression test, then verify the affected repository
and the successful sentinels on one combined HEAD. This preserves the product
while avoiding repeated full-cohort execution.

### Rejected: broad timeout and resource expansion

Increasing clone, Observer, Boot, memory, and readiness limits together would
hide which boundary mattered and would make hangs more expensive. Bounded
values may change only after their own evidence gate.

### Rejected: repository-specific compatibility rules

Branches on repository ID, URL, commit SHA, image, or service would optimize the
benchmark instead of improving RepoTrial. They remain prohibited.

## 5. Frozen boundaries

The continuation must not:

- reorder, replace, or modify the frozen ten-repository manifest;
- mutate a source Compose file in place;
- execute target Compose on the host;
- expose a host Docker socket, credentials, model keys, SSH material, LAN
  resources, or metadata endpoints to a target;
- add host fallback or an unbounded retry;
- reinterpret missing evidence as success;
- weaken exact-SHA, Journey assertion, KEEP/ROLLBACK, cleanup, stop-reason, or
  report-evidence requirements;
- change LangGraph orchestration, M5 Engine contracts, M6 checkpoint semantics,
  or M7 API/CLI/report semantics as an incidental compatibility fix;
- update release wording in `README.md` before every final gate passes;
- claim global safety or least privilege.

Historical evidence remains append-only. New diagnostic attempts are
`diagnostic-only`; they are not metric-bearing replacements. Production
changes supersede earlier metric-bearing epochs only prospectively, and the
final ten-repository cohort is the sole source of release metrics.

## 6. Execution funnel

### Stage A: current-HEAD diagnostic recertification

Run Linkding and changedetection.io serially on the current reviewed HEAD after
the normal repository and sandbox preflight. These runs answer only:

1. Can Intake verify the exact frozen SHA now?
2. Does the workload reach Boot?
3. Which next deterministic boundary is reached?
4. Does cleanup finish with exact empty inventory?

Linkding may demonstrate that the already-reviewed startup-input materializer
reaches its intended real target. changedetection.io may supply the missing
target-side three-layer publication evidence. Neither result changes historical
attempt attribution or directly contributes release metrics.

Paperless-ngx may receive a current-HEAD diagnostic only if inspection shows
that the existing generic startup-input materializer already applies without a
new policy. This is verification of existing behavior, not authorization to
synthesize a new secret rule.

### Stage B: Uptime same-origin redirect correction

This design explicitly authorizes a narrow Journey execution-semantic extension
after a diagnostic proves Uptime's `Location` is valid and same-origin.

The correction must:

- apply only to `GET`; the Journey DSL is not expanded with `HEAD`;
- recognize only `301`, `302`, `303`, `307`, and `308`;
- follow at most three redirects;
- establish one five-second monotonic step deadline immediately before the
  initial request; connection, response headers, every redirect, and the final
  bounded body read all consume that single budget;
- require identical scheme, host, and effective port on every hop;
- reject missing, duplicate, malformed, cyclic, credential-bearing, control
  character, backslash, encoded traversal, or origin-changing `Location`;
- resolve each `Location` relative to the current URL, then apply the complete
  existing path/query policy or a stricter equivalent to the resulting request
  target on every hop; reject fragments, network-path references such as
  `//host/path`, literal or repeatedly decoded `.` and `..` segments,
  targets over 2048 characters, and every form rejected by the current grammar;
- disable cookie persistence and never propagate authorization, request bodies,
  or target-controlled headers between hops;
- close each intermediate response before the next request without reading or
  persisting its body;
- preserve explicit redirect assertions: if the declared status assertion
  expects the observed redirect status, evaluate that response without
  following it;
- otherwise evaluate the original status/text/JSON assertions only against the
  final bounded response;
- never treat the intermediate `302` itself as a successful `200`;
- preserve one exclusively created `step-NNNN.json` artifact and add only a
  bounded hop summary containing status and a sanitized target hash, never a
  raw `Location`.

RED tests must cover a valid relative same-origin redirect and every security
rejection above. Existing explicit-`302` and cross-origin tests must remain
unchanged and pass.

### Stage C: n8n Observer diff calibration

No timeout value changes before calibration.

The diagnostic uses identically configured fresh n8n sandboxes and a trusted
writable-layer fixture. It covers every discovered n8n container, records the
exact `docker diff` operation duration, and tests candidate ceilings in the
order `60`, `120`, then `180` seconds. Select the smallest candidate that
meets every gate. A failed 60-second candidate alone permits testing 120; a
failed 120-second candidate alone permits testing 180. A candidate is eligible
only when:

- all n8n container diff operations complete successfully in three consecutive
  repetitions using the same frozen workspace, SHA, policy, and workload state;
- the trusted fixture demonstrates the same generic slow-diff boundary;
- the original 30-second failure, owned child kill/reap, total-deadline
  remainder, bounded output behavior, lifecycle, and cleanup are retained;
- final inventory is exactly empty.

Each repetition receives a fresh sandbox. Any timeout, cancellation, malformed
result, cleanup uncertainty, or other provider error immediately ends that
sandbox. The next repetition or candidate may start only after destroy is
confirmed and the official inventory is exactly empty. The trusted fixture uses
the same candidate ordering, three-success rule, and fresh-sandbox lifecycle.

If eligible, production may split only
`_DIFF_TIMEOUT_SECONDS` from the existing shared Observer timeout. Discovery,
inspect, and top remain at 30 seconds. The Provider still enforces:

`min(diff_timeout, whole_trial_deadline_remaining)`.

Timeout or malformed output still fails; the implementation must not invent an
empty diff or mark an unobserved filesystem as unchanged. If no candidate
passes the calibration gate, no Observer production change is made.

### Stage D: changedetection publication diagnosis

The target must first verify its exact SHA and reproduce all three observations
on the same port:

1. target-container loopback succeeds;
2. sandbox-guest loopback succeeds;
3. Provider-published loopback fails with the same allowlisted network failure
   class as the trusted fixture.

This design does not authorize a Provider lifecycle adapter or a
`publish_port()` contract change. If the target gate passes, the next bounded
design is the already-described immutable Compose compatibility artifact:
parsed Compose transformation, separate artifact and hash, source immutability,
fail-closed ambiguous mappings, and identical baseline/Journey/candidate use.

### Stage E: deferred failure domains

Paperless, Wakapi, and NetBox do not receive production changes merely because
the success count is short.

- Paperless requires a separate root-cause design proving generic Compose
  detection, guest-only secret generation, no plaintext persistence,
  baseline/candidate identity reuse, and checkpoint/resume behavior.
- Wakapi requires a repeatable successful interval and a healthy target result;
  merely waiting long enough to receive `unhealthy` is not recovery.
- NetBox requires evidence for the migration kill before memory, readiness, or
  resource policy changes.

Each domain is opened only by its own reproducible evidence.

## 7. Acceptance and regression gates

Every behavior-changing task is serial and uses:

1. one evidence-backed hypothesis;
2. RED before production code;
3. minimal GREEN and self-review;
4. focused tests;
5. Ruff lint and format, mypy, full pytest, and branch coverage at least 85%;
6. an independent Sol-high review with no open Critical or Important finding;
7. an affected real-repository canary and exact empty inventory.

Execution work is assigned to Luna-max; planning and independent review use
Sol-high. Agents are closed after their result is accepted.

After every accepted production correction, the latest HEAD runs the directly
affected repository plus any former failures already passing in the current
diagnostic epoch. After all selected corrections, the combined HEAD must rerun
Umami, Listmonk, and Dockge. A regression in any sentinel rejects the combined
HEAD. The controller then attributes it by comparing correction-specific diffs
and running a focused sentinel canary against each preceding accepted HEAD in
an isolated worktree; no final combination is accepted until the regression is
removed and the three sentinels pass again.

Diagnostic admission requires at least four of the seven former failures to
meet the complete autonomous-success predicate on one combined HEAD. These
canaries are not final release metrics. Once admission passes, run the frozen
ten-repository cohort once in manifest order. It alone must prove Stage 1
`>=7/10`, exact SHA, stop reasons, cleanup, empty inventory, and no host
fallback.

## 8. Stage 2 and final release

After Stage 1 passes, resume the accepted Stage 2 structure from the original
release-gap design:

1. build the complete rollback evidence matrix;
2. select the largest evidence-supported generic mutation failure class;
3. correct one mutation class through a separate TDD task;
4. rerun successful Stage 1 repositories on the new reviewed HEAD;
5. require meaningful convergence on at least five frozen repositories.

The final unified HEAD then passes all repository quality gates, scoped SBX
integration gates, secret scans, manifest/lock fingerprints, and a final
independent code and claims review before one final metric-bearing cohort.
`README.md` changes only after the mechanical final ruling passes.

## 9. Stop conditions

Stop and request a new Owner decision if:

- a correction requires a frozen public contract change not explicitly
  authorized in this design;
- a target requires a repository-specific branch or secret;
- cleanup, exact SHA, or no-host-fallback cannot be proven;
- a change regresses Umami, Listmonk, or Dockge;
- the same compatibility hypothesis fails after one implementation attempt;
- a module needs a second unrelated production correction;
- the SBX daemon requires start, stop, restart, or reset;
- the final cohort completes.

The controller may move to the next evidence-supported domain after a rejected
hypothesis without asking for another authorization, provided no stop condition
above applies.
