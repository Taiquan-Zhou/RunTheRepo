# M7.5 Real-Repository Compatibility Recovery Design

## Status

Owner-approved design, independently reviewed before implementation.

## Goal

Recover RepoTrial's real-repository compatibility without reopening M0-M7.4 or
changing the product architecture. A public GitHub repository pinned to an exact
commit must progress through isolated Boot, at least one deterministic Journey,
evidence-backed hardening experiments, report generation, and forced cleanup.

The release target remains the frozen ten-repository cohort on one production
HEAD:

- autonomous success: at least 7/10;
- meaningful regression-safe convergence: at least 5/10;
- exact stop-reason coverage: 10/10;
- cleanup success: 100% of cleanup obligations;
- no host fallback and no repository-specific workaround.

## Evidence-backed problem statement

The current unified baseline is commit
`54481329c60b1a5fcb56650e246b0531583a1403`. It includes the frozen cohort,
Disk Bound, whole-trial monotonic duration enforcement, exact-SHA enforcement,
public SBX egress compatibility, and the retained pre-fix/post-fix Pilot ledgers.

The post-fix cohort produced zero autonomous successes. Eight repositories
ended at `boot_recovery_stopped`, one timed out in sandbox execution, and
Paperless-ngx stopped at `intake:clone`. The retained artifacts do not contain
the three Boot command exit codes and bounded stdout/stderr, the recovery
proposal rationale, or the reason the action was not applied. Consequently,
the exact remaining Boot causes cannot be reconstructed.

Current code also proves two compatibility gaps without relying on old reports:

1. `repotrial inspect` passes `readme_excerpt=""` and
   `allowed_env_keys=frozenset()` to `GraphContext`, so the no-model recovery
   path cannot use the pinned repository's README, Compose interpolation, or
   root `.env.example` declarations.
2. `boot_compose()` runs `compose up -d` and immediately samples `compose ps`.
   The deterministic planner then proposes host-side sleep for generic
   "starting" text. That sleep is outside the sandbox workload command and is
   not the trusted readiness primitive.

These observations justify evidence collection. They do not justify changing
readiness or recovery behavior before a real diagnostic canary identifies the
dominant failure class.

## Architecture boundary

The implementation remains inside existing Trial/Graph responsibilities:

- a private Boot-attempt evidence artifact;
- a private bounded recovery-evidence projection;
- deterministic repository context derived from the already pinned workspace;
- a Docker Compose readiness mode, only when the installed SBX guest Compose
  proves official support;
- focused tests and Pilot evidence updates.

The following contracts do not change:

- LangGraph topology and public orchestration semantics;
- `RunState` and `GraphState` checkpoint schemas;
- M5 experiment decision, KEEP, and ROLLBACK semantics;
- M7 report JSON/HTML, API, and CLI semantics;
- `SandboxProvider` interface;
- Journey, mutation, and report evidence models;
- frozen repository manifest, order, URLs, SHAs, and metric attribution rules.

`boot_compose()` is shared by baseline Boot and M5 candidate Boot. Any readiness
correction therefore applies consistently to both paths. Candidate decision and
KEEP/ROLLBACK logic remain unchanged. If implementation requires modifying
`src/repotrial/hardening/engine.py` production behavior rather than inheriting
the shared Boot correction, implementation stops for an architecture ruling.

## 1. Private Boot-attempt evidence

Every baseline Boot attempt gets `baseline-boot-attempt.json` in its already
claimed attempt directory. The artifact is private diagnostic evidence and is
not added to `RunState`, Graph checkpoints, or the public report schema.

Schema version 1 contains:

- attempt number and Compose path;
- logical command name (`up`, `ps`, `logs`) and command phase;
- exit code or sanitized exception class;
- separately redacted and bounded stdout/stderr views with truncation flags;
- parsed service states and deterministic readiness result;
- final Boot verdict when available;
- recovery action, bounded rationale, application disposition, and resulting
  stop reason when recovery planning occurs.

Evidence limits are UTF-8 byte limits, not character limits:

- `DockerSbxProvider` drains each stdout/stderr stream while retaining a
  deterministic bounded head and tail, rather than an irreversible prefix;
- the artifact stores stdout and stderr separately, including a truncation flag;
- each persisted stream view is at most 32,000 UTF-8 bytes;
- all six stream views total at most 192,000 UTF-8 bytes;
- schema/metadata overhead is reserved before the final UTF-8 JSON artifact's
  hard limit of 262,144 bytes is enforced;
- environment values never appear in recorded argv or metadata;
- every non-empty runtime environment value is redacted from diagnostic streams,
  independent of the environment key's name;
- raw provider output is never written to the destination or an atomic-write
  temporary file.

Persistence is checkpointed after each command result. If provider execution
raises, the artifact records only a sanitized exception class and re-raises the
original error. Evidence persistence failure is fatal and still passes through
`managed_sandbox` cleanup. Cleanup failure remains represented by the existing
lifecycle artifact and is never hidden by a later evidence rewrite.

The frozen public `boot_compose()` signature remains unchanged. Graph uses a
private `_boot_compose_with_evidence()` entry point; both delegate to the same
private implementation so baseline and candidate command/readiness behavior
cannot diverge.

Truncation is explicit evidence. If the causal stream was truncated and the
exact cause is not visible in retained head/tail evidence or independently
corroborated, the attempt is category E (insufficient evidence) and cannot
authorize a production correction.

## 2. Diagnostic canary before behavior changes

After evidence instrumentation is reviewed and committed, run the first three
frozen repositories in manifest order: Umami, Listmonk, and
changedetection.io. These attempts are `diagnostic-only` and do not replace or
alter prior metric-bearing results.

For each repository extract:

- first failed command and exit code/exception class;
- bounded Compose stdout/stderr;
- parsed service states and logs;
- recovery proposal and exact stop disposition;
- cleanup result and final empty/non-empty SBX inventory.

The next production change must address one dominant generic cause represented
in at least two of the three diagnostic attempts. “Same cause” requires the same
command/phase, compatible exit code or exception class, and the same normalized
causal signature. A broad A-E report category alone is not a repair signature.
For a missing-environment cause, evidence additionally records the pinned SHA,
declared key, root-relative declaration source, and source-file SHA-256; values
are never recorded. If no such cause exists, stop and revise the implementation
plan from retained evidence; do not implement context/readiness changes by
assumption.

## 3. RecoveryEvidenceView

The persisted Boot artifact retains full bounded evidence. Recovery planning
receives a smaller deterministic projection so the current 65 KiB Boot output
cannot violate the planner's 4 KiB-per-field / 16 KiB aggregate boundary.

Projection rules:

- fixed command order: `up`, `ps`, `logs`, followed by sorted unknown keys;
- at most 32 entries and 128 characters per key;
- at most 4,096 characters per value;
- long values retain deterministic head and tail sections separated by one
  truncation marker;
- aggregate projected value content is at most 16,384 characters;
- projection happens after redaction; it never accepts raw provider output.

The original `BootResult.logs` and private artifact remain unchanged. Only the
projection is passed to `propose_recovery()` and the error fingerprint.

## 4. Deterministic pinned-repository recovery context

Context is derived only after Graph `_intake` has pinned the requested exact
commit into `GraphContext.workspace`. The CLI must not perform a second checkout
or pre-scan a floating repository.

A private `RecoveryRepositoryContext` contains only a bounded allowlist of
environment-variable names declared by Compose interpolation or root
`.env.example`, plus root-relative declaration paths and source hashes for
audit correlation. It does not provide README text to Journey planning.

Trust rules:

- root files only; no recursive documentation search;
- regular files only; links/reparse points are rejected;
- maximum source size 65,536 bytes and UTF-8 text only;
- `.env.example` contributes names only, never values;
- `.env`, host environment, credentials, and arbitrary README commands are
  never read or executed;
- Compose interpolation supports declared forms such as `${NAME}`,
  `${NAME:-default}`, `${NAME-default}`, `${NAME:?error}`, and `${NAME?error}`;
- keys are portable environment names, sorted, and limited to 32 entries.

Fallback is computed once per Boot node invocation. Explicitly supplied
non-empty `allowed_env_keys` win; only an empty allowlist is replaced with
derived pinned-repository declarations. `readme_excerpt` is unchanged by this
recovery task.

Synthetic values remain allowed only when sanitized runtime evidence explicitly
identifies a missing key that is present in the allowlist. Repository context
alone never causes an environment variable to be injected.

## 5. Pinned README input for deterministic Journey planning

The CLI currently supplies an empty README excerpt, which leaves real
repositories without declared `repotrial.journeys.json` unable to produce the
non-empty deterministic Journey set required by the frozen success definition.
README derivation is therefore a separate compatibility change, never a side
effect of recovery env authorization.

It is eligible only when diagnostic evidence shows at least two exact pinned
repositories have no declared Journey file, receive an empty explicit excerpt,
and contain a valid real root README. The derived excerpt is passed only to the
existing `plan_journeys()` boundary after `_intake`; it does not enter
`propose_recovery()` in no-model mode and does not expand tool authority.

The change must prove that Journey DSL validation, deterministic verifier
semantics, and the frozen rule “non-empty required baseline Journey set and all
required Journeys PASS” remain unchanged.

## 6. Trusted readiness and `wait` compatibility

Readiness may use only the official guest Docker Compose capability proven by
the installed SBX runtime. The calibration command is `docker compose up --help`
inside a disposable trusted fixture sandbox. Support requires both documented
`--wait` and `--wait-timeout` options and a real fixture PASS using:

```text
docker compose -f compose.yml up -d --wait --wait-timeout 60
```

If support is proven, `boot_compose()` uses that command for both baseline and
candidate Boot while retaining the existing provider per-command timeout and
whole-trial host monotonic deadline. It still runs deterministic `ps` and `logs`
afterward. All declared services must remain running and healthy when a health
check exists. An exited service remains fail-closed; support for successful
one-shot services requires separate evidence and a separate design based on
Compose dependency semantics.

If the installed guest Compose does not support this capability, readiness work
stops. No host sleep polling, shell loop, new Provider method, watchdog, or
repo-specific workaround is permitted.

Calibration evidence is committed with the change and includes the execution
HEAD, SBX and guest Compose versions, bounded complete help output, delayed
fixture argv/exit/service-health result, lifecycle cleanup, and final empty
inventory.

`RecoveryAction` continues to accept `wait` at its frozen schema boundary for
checkpoint/model compatibility. The deterministic planner stops generating
`wait`. If Graph receives a `wait` action, it fails closed, records that the
action is unsupported by the trusted recovery executor, and terminates with the
existing Boot stop semantic. `GraphContext.sleep` is then removed as an unused
internal hook; no public state or checkpoint field changes.

## 7. Validation ladder

Each production behavior uses strict RED -> GREEN -> REFACTOR. Every task gets
an independent implementer and reviewer. Completion requires:

- focused unit/integration tests;
- candidate-Boot regression coverage for shared readiness behavior;
- Ruff check and format check;
- strict mypy;
- coverage at least 85%;
- pre-commit and `git diff --check`;
- comparison against the established Windows full-test baseline, with zero new
  regressions;
- a real trusted SBX lifecycle smoke with final empty inventory.

After all behavior changes, freeze one execution HEAD and start the final cohort.
Repositories #1-#3 are simultaneously the canary and the final cohort's first
three metric-bearing attempts. A success requires exact SHA, a non-empty
deterministic required baseline Journey set, every required baseline Journey
PASS and be persisted, completed report evidence, and successful cleanup. At
least 2/3 must satisfy that criterion before execution continues with #4-#10.

No commit or production/document change occurs between #1 and #10 when the
canary passes. If the canary fails, record and commit its failure evidence and
stop. Any production-code change after a metric-bearing attempt supersedes the
whole cohort and requires a complete rerun on the new unified HEAD. Historical
attempts remain append-only audit evidence.

## Non-goals

- no full-project rewrite or broad refactor;
- no new sandbox backend or Provider interface;
- no host Docker fallback;
- no repository-name branches or repository-specific scripts;
- no README-driven shell execution;
- no model integration in this compatibility recovery;
- no PID-limit claim beyond the disclosed Docker SBX limitation;
- no README release claim before the frozen cohort reaches its existing gate.
