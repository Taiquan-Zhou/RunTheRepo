# M7.5 Post-Pilot Recovery Design

## Status and authority

Owner-approved design recorded after the first complete frozen-cohort run at
execution HEAD `7f1f401bc749f9bcce8e4bbc9287071ccc3a758c`. The current documentation
HEAD is `183069f0de2c61dac27393bb1cc5f4942ea3e383`.

This design authorizes a bounded recovery of the existing M7.5 implementation.
It does not reopen M0-M7.4 and does not replace RepoTrial's architecture. The
existing product target, deterministic Journey verifier, KEEP/ROLLBACK
acceptance, exact-SHA intake, Docker SBX isolation, disk hard bound,
whole-trial monotonic deadline, forced cleanup, and no-host-fallback rules
remain authoritative.

Owner additionally limits repository recovery execution to at most two
repositories at a time. This is one global limit across diagnostic, calibration,
canary, and final-cohort execution. The default is serial execution. Two-way
concurrency is permitted only when executions do not share a mutable SBX
sandbox, artifact directory, checkout, or calibration variable.

## Final product and M7.5 target

RepoTrial remains:

```text
public GitHub URL
-> exact pinned commit
-> disposable isolated Docker Compose trial
-> bounded model-assisted planning
-> deterministic Journey verification
-> bounded permission experiments
-> KEEP or ROLLBACK from deterministic evidence
-> evidence-backed report
-> forced cleanup
```

M7.5 is complete only when a single final production HEAD and the frozen
ten-repository manifest prove:

- autonomous success at least `7/10`;
- meaningful regression-safe convergence at least `5/10`;
- exact terminal stop reason `10/10`;
- cleanup success `100%` within the final unified execution epoch;
- no host Docker fallback or repository-specific workaround;
- all retained historical attempts remain visible in the audit ledger;
- the known unsupported PID hard bound is disclosed and never emulated.

If the frozen cohort honestly cannot meet the functional thresholds after the
bounded recovery below, RepoTrial must report the remaining limitation. It may
not weaken a verifier, replace a repository, mix production HEADs, or relabel a
failure to obtain the target.

## Evidence from the first full cohort

The first full cohort produced one autonomous success and zero KEEP results.
Only three repositories completed a baseline, so five KEEP results were
mathematically impossible in that run.

The dominant evidence is split across independent boundaries:

1. Uptime Kuma, n8n, and NetBox failed during image acquisition or extraction
   with exact Docker-data `No space left on device` evidence. The current
   2,048 MiB total maps to 1 MiB root, 1,919 MiB Docker data, and 128 MiB
   workspace. The evidence proves the current default is insufficient for the
   frozen cohort but does not yet prove a replacement value.
2. Umami and Listmonk reached about 308 seconds and then recorded an experiment
   `sandbox_failed`. Provider operation/reason and deadline state were flattened,
   so total-duration exhaustion is plausible but not proven.
3. Paperless-ngx passed host exact-SHA and cleanliness checks but failed guest
   clone verification with `guest_status_not_clean`. The tracked paths and mode
   differences were discarded, so a safe correction cannot yet be selected.
4. Wakapi failed clone intake without a preserved sanitized failure class.
5. Every observed permission candidate for ordinary applications began with
   `SET_NON_ROOT` because `root_user_possible` maps to a fixed
   `65532:65532`. That mutation does not account for image users, volume
   ownership, or required writable paths and is a proven candidate-quality
   bottleneck, not a verifier defect.
6. Linkding's missing `.env` and changedetection.io's loopback-only published
   port are distinct compatibility classes. They are not part of the initial
   correction because safe generic materialization or networking semantics are
   not yet established.

## Selected approach

Use an evidence-first staged correction inside existing modules. Restore exact
private diagnostics, calibrate the existing bounded resources, correct the
existing mutation candidate policy only when cross-repository evidence confirms
the cause, and then run one unified cohort.

A resource-only change is insufficient because it does not address zero KEEP
convergence. Adding missing-env materialization and loopback rewriting now would
combine unrelated compatibility contracts before the dominant failures are
resolved. Those capabilities remain separate follow-up design gates if the
bounded recovery still cannot reach the frozen threshold.

## Stage 1: preserve private failure evidence

### Sandbox and experiment failures

Preserve bounded structured fields from `DockerSbxError` in private lifecycle
or diagnostic artifacts:

- operation and reason;
- elapsed and remaining monotonic trial budget;
- whether the command timeout was deadline-limited;
- whether a workload subprocess was started.

Failure and cleanup are separate append-only events. The provider failure event
is written when the failure becomes known. The managed-lifecycle terminal event
is written only after destroy or cleanup retry completes. Attempt ID and, when
owned, sandbox ID correlate the events; aggregation derives the complete
outcome without pretending cleanup was known when the exception was created.

The public report schema, experiment verdict, RunState, checkpoint schema, and
`SandboxProvider` interface do not change. Raw untrusted stderr, secrets, host
paths, or unlimited output must not be copied into structured state.

### Clone verification failures

When guest tracked status is non-empty, preserve bounded private metadata:

- porcelain status code and root-relative tracked path;
- raw diff status, old/new mode, and blob identifiers;
- host and guest `core.filemode`, `core.autocrlf`, and `core.symlinks` values;
- explicit entry and UTF-8 byte limits with a `truncated` marker.

Do not preserve file contents. Verification remains fail-closed and cleanup is
still mandatory.

### Intake clone failures

Preserve a sanitized bounded clone failure class such as transport, DNS, HTTP,
authentication, missing commit, checkout, or local I/O. Do not expose remote
credentials or retain arbitrary stderr.

## Stage 2: calibrate bounded resources

### Disk

Use the three frozen ENOSPC repositories as failing calibration cases. The
pre-registered total-disk candidate sequence is `2048, 3072, 4096, 6144, 8192`
MiB and the ceiling is `8192` MiB. Hold the execution HEAD, repository SHA,
Compose path, image identity, CPU, memory, network, disk allocation formula, and
cleanup rules constant. Record the allocation implementation hash and the exact
root/Docker/workspace result for every candidate.

For each candidate record Docker/workspace capacity after clone, image
acquisition, and healthy Boot. A disk-calibration PASS requires exact-SHA clone,
no disk-capacity error, healthy Compose Boot, successful required baseline
Journeys, cleanup PASS, and empty final inventory. Stop each repository after
its first PASS.

Let `F` be the largest first-PASS candidate among the three failing repositories.
The proposed default is the next value after `F` in the pre-registered sequence;
that deterministic one-step reserve is the complete margin rule. If `F` is
`8192`, calibration is unsupported and does not change the default. Confirm the
proposed default with one additional run of each failing repository, one Umami
tight-boundary control, and one lighter already-passing control. Every
confirmation must satisfy the same PASS matrix. The value remains one
`SandboxPolicy.disk_mb`, maps through the existing official SBX environment
variables, and remains a hard total bound.

### Whole-trial duration

First use Stage 1 evidence to determine whether Umami and Listmonk ended with
`total_duration_exhausted`. If not, do not change the default for those failures.
If confirmed, use the pre-registered duration sequence `300, 450, 600, 900`
seconds with a `900` second ceiling and retain the existing experiment budget.
Normal termination means exact-SHA baseline and required Journeys pass, every
started experiment ends through the existing KEEP/ROLLBACK/experiment-budget/
consecutive-failure path rather than `total_duration_exhausted`, an exact stop
reason is retained, cleanup passes, and final inventory is empty.

Let `T` be the largest first-normal-termination value for the confirmed
deadline-only repositories. The proposed default is the next value after `T` in
the pre-registered sequence. If `T` is `900`, calibration is unsupported and
does not change the default. Confirm the proposed value with one additional run
of each deadline-only repository using the same acceptance matrix.

The host-side shared monotonic deadline remains the trusted enforcement. It is
not reset per experiment. Existing per-command timeouts remain in force, and
destroy/failure cleanup continues outside the exhausted trial deadline.

Changing either default is an Owner-approved C2 safety-budget ruling under this
design. Calibration chooses the value; it does not authorize an unbounded or
adaptive runtime budget.

## Stage 3: correct mutation candidate grounding

The deterministic verifier and experiment engine are not changed.

Stage 1 must first prove across at least two independent repositories that the
fixed-UID candidate caused the Boot or Journey regression. That evidence
authorizes only removal of the uncertain finding's fixed-UID trigger:

- an explicit `root_user` finding may continue to propose `SET_NON_ROOT`;
- `root_user_possible` no longer proposes fixed UID `65532:65532`;
- an explicit `cap_add` finding continues to propose `DROP_ALL_CAPS`;
- no alternative magic UID is introduced;
- the same immutable baseline Journey artifact is replayed;
- Boot or Journey regression remains ROLLBACK.

Separately, the Owner authorizes one existing `DROP_ALL_CAPS` default-capability
ablation candidate for a service reported as `root_user_possible`. This is an
explicit M5 least-privilege experiment over the ordinary Linux container
default capability set, not an inference that fixed-UID failure proves a
capability defect. It remains subject to the existing experiment ordering,
budget, immutable Journey replay, and deterministic ROLLBACK gate. It adds no
mutation type or parameter.

This is a correction to candidate selection inside the existing M5 mutation
set. It does not add a mutation type, change evidence schemas, relax acceptance,
or guarantee a KEEP result. A future evidence-driven UID/GID parameter would
require a separate Owner design ruling and is not authorized here.

## Stage 4: bounded clone correction

Use the Stage 1 evidence to determine whether Wakapi and Paperless-ngx expose a
generic cross-repository or cross-platform defect. Implement only a correction
that preserves exact commit identity and clean tracked contents.

Forbidden corrections include ignoring dirty state, automatic reset/checkout,
repository-name branches, copying host credentials, or treating a clone failure
as success. If evidence remains repository-specific or inconclusive, retain an
exact `unsupported`/failure reason and do not patch it.

## Cleanup metric supersession

The Owner explicitly supersedes the earlier all-historical-attempt cleanup
denominator with the following two simultaneous views:

1. **Final candidate-HEAD release epoch:** every cleanup obligation produced by
   diagnostic, calibration, canary, and metric attempts on the final candidate
   production HEAD, including the complete ten-repository run. This value must
   be `100%`, and every post-attempt inventory must be empty, for the M7.5
   release gate.
2. **Lifetime audit ledger:** every retained historical, diagnostic, audit-only,
   superseded, and metric-bearing attempt. Historical failures remain visible
   and are never deleted or rewritten, but they do not make a repaired future
   production HEAD permanently incapable of passing its own release gate.

Existing per-attempt lifecycle JSONL remains the source of truth. The M7.5 pilot
report lists both denominators, production HEADs, attempt IDs, derived cleanup
outcomes, and final inventory evidence explicitly. No application JSON/HTML
report schema changes. A cleanup failure on the current candidate HEAD blocks
release unless a production correction creates a new candidate HEAD; the failed
attempt then remains in the lifetime ledger under its superseded HEAD.

## Execution and concurrency protocol

- Use the existing isolated worktree and a single controlled production branch.
- Follow RED -> GREEN -> REFACTOR for every behavior change.
- Commit each independently reviewable stage before using it for real evidence.
- Run repository recovery serially by default.
- Enforce global `in_flight_repositories <= 2` across every execution phase.
- Enforce `in_flight_repositories <= 1` while calibrating the same resource
  variable.
- Permit only one active trial/sandbox for a given repository.
- Concurrent cases must have disjoint workspaces, artifact roots, and sandbox
  IDs and must not calibrate the same variable.
- Do not start, stop, restart, or reset the SBX daemon.
- A production change after metric-bearing execution supersedes the complete
  metric cohort. All previous attempts remain audit evidence.
- Before the final cohort, run the frozen three-repository canary and require at
  least `2/3` autonomous compatibility success.
- Run the final ten repositories in frozen order, retaining every result. At
  most two independent repositories may be in flight during the final cohort.
- Freeze calibrated defaults before the canary. Canary and final cohort validate
  those values and never tune them from observed outcomes.

## Verification gates

Each implementation stage requires focused RED/GREEN tests, scoped lint/type
checks, controller diff review, and a separate Reviewer. Before the final cohort
the unified HEAD must pass:

```text
uv run ruff check .
uv run ruff format --check .
uv run mypy src/repotrial
uv run pytest -q
configured coverage gate >= 85%
pre-commit
git diff --check
```

Real SBX calibration and smoke evidence must prove exact SHA, hard disk bound,
shared total-duration enforcement, forced cleanup, empty final inventory, and
no host fallback.

## Frozen boundaries

This design does not authorize changes to:

- LangGraph topology;
- M5 acceptance, KEEP/ROLLBACK, experiment count, or consecutive-failure stop;
- M6 RunState or checkpoint semantics;
- Journey DSL, deterministic verifier, artifact hash, or replay identity;
- public application report/API/CLI semantics, except calibrated default policy
  values; the Owner-approved cleanup denominator supersession is recorded only
  in M7.5 evaluation reporting;
- frozen repository manifest, order, URL, SHA, Compose path, or metric target;
- SandboxProvider interface or Docker SBX daemon lifecycle;
- PID limitation disclosure or any safety fallback.

Missing `.env` materialization, loopback-port compatibility, mutation parameter
expansion, or any other new capability requires a separate bounded design if the
approved recovery proves it is still necessary.
