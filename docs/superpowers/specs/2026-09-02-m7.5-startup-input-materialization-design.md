# M7.5 Startup-Input Materialization Design

**Status:** Diagnostic gate passed; implementation is blocked pending an
explicit Owner policy decision.

**Scope:** A deterministic, guest-local materializer for a missing required
service-level `.env` file when a bounded repository-local `.env.sample` exists.
This design does not authorize implementation, change the frozen cohort, or
execute repository instructions.

## 1. Evidence and problem statement

At Linkding commit `65813a75404b1319aca8b09700fadc0b15adabaf`,
`docker-compose.yml` declares required service-level `env_file: .env`.
The target `.env` is absent. The checked-in `.env.sample` is a 2,090-byte,
regular, non-linked UTF-8 file with SHA-256
`12a0e13fc1b005ea484b96c666813d1a601de5ad85c9db82262b67950dcb10bf`.
Its values classify only as empty, boolean, integer, repository-relative path,
or local literal. A disposable-guest inspection proved that the target's
resolved parent remains the verified clone root and did not create the target.

The unchanged product run again failed before workload startup because `.env`
did not exist. The RG2 diagnostic entry gate therefore passes. This proves the
boundary; it does not authorize a materializer or count a recovery.

## 2. Mandatory Owner policy decision

All 20 Linkding template keys begin with `LD_`. The approved release-gap design
currently says that a deferred materializer must reject every `LD_*` key. No
implementation can both retain that rule and materialize Linkding's template.

The Owner must choose exactly one option before an implementation plan, RED
test, or production edit:

### Option A - Retain the frozen prefix rule

- Keep rejecting every `LD_*` key in every context.
- Do not implement the Linkding materializer.
- Record Linkding as unsupported under the current startup-input policy and
  continue the release-gap process without counting it as recovered.

### Option B - Approve filtered guest-file materialization

- Keep the existing host command-environment rules unchanged, including the
  broad `COMPOSE_*`, `DOCKER_*`, `DYLD_*`, and `LD_*` rejection in
  `_validated_env_prefix()` and model-recovery `set_env` validation.
- In the guest file, never copy, synthesize, or export any assignment whose
  normalized key is `PATH`, `HOME`, `PYTHONHOME`, `PYTHONPATH`, or
  `XDG_CONFIG_HOME`, or starts with `COMPOSE_`, `DOCKER_`, `DYLD_`, or `LD_`.
  Such assignments are omitted from the generated file and their key names are
  retained in the audit record. This closed prefix rule also omits unknown or
  future dynamic-loader variables; there is no loader-variable allowlist.
- Parse and validate every source assignment before filtering. A malformed,
  duplicate, oversized, linked, escaping, or otherwise unsupported source still
  rejects the whole materialization. Filtering is not a parser-error fallback.
- Permit an empty generated file. Linkding can then use its checked-in Compose
  `${NAME:-default}` expressions while the required service `env_file` exists.
  If a repository instead needs an omitted key, Compose validation or Boot fails
  normally; RepoTrial does not invent a value or retry with a weaker policy.
- Apply this rule to every repository. No URL, SHA, service-name, key-name, or
  Linkding-specific allowlist is permitted.

Option B changes the frozen behavior from rejecting a template containing a
control key to safely omitting that key from a guest-only file. It therefore
requires explicit Owner approval plus an independent security review. General
design approval is not a substitute for that decision.

## 3. Non-goals and frozen contracts

The implementation must not:

- execute README prose or repository scripts;
- read host environment values or real credentials;
- add a host-to-guest `SandboxProvider.copy()` direction;
- alter `SandboxProvider`, LangGraph topology, M5 engine semantics, M6
  `RunState`/checkpoint fields, M7 API/CLI/report semantics, Journey semantics,
  mutation selection, or KEEP/ROLLBACK decisions;
- mutate the host source clone or source Compose file;
- add a repository-specific condition or fallback;
- claim support for arbitrary env syntax or arbitrary setup instructions.

## 4. Accepted input boundary

The proposed MVP accepts only this deterministic shape:

1. The already-selected Compose document has a service-level, required,
   repository-relative `env_file` entry naming `.env`.
2. `.env` is absent and is not a symlink or reparse point.
3. Its resolved parent is the verified guest clone root.
4. Exactly one `.env.sample` exists in that same directory.
5. The source is a regular, non-linked UTF-8 file no larger than 64 KiB, with
   at most 64 assignments and a maximum logical line length of 4 KiB.
6. Lines are blank, comments, or portable `KEY=VALUE` assignments. Duplicate
   keys, NUL/control characters, `export`, quoting, continuation, interpolation,
   command substitution, backticks, and shell syntax fail closed.
7. Values may be empty, booleans, decimal integers, bounded local literals, or
   normalized repository-relative paths that do not escape the clone.
8. A non-empty value whose non-control key is secret-looking (`password`, `secret`,
   `token`, or `api_key` components) is never copied; it is replaced with the
   existing constant `repotrial-synthetic-value`. Empty sensitive values remain
   empty. No host value is consulted.
9. Control-key handling follows the Owner-selected policy in Section 2. Under
   Option B, control assignments are validated and audited by name but omitted
   from the output; they are never exposed to either a trusted host process or
   an untrusted container process by this materializer.

Any ambiguity, unsupported syntax, multiple source candidates, pre-existing
target, path escape, source change, hash mismatch, or artifact collision is
`UNSUPPORTED`; Boot is not started.

## 5. Typed internal model

A new private module `src/repotrial/trial/startup_inputs.py` may define:

```python
@dataclass(frozen=True, slots=True)
class StartupInputPlan:
    source_relative_path: str
    target_relative_path: str
    source_sha256: str
    output_sha256: str
    accepted_key_names: tuple[str, ...]
    synthetic_key_names: tuple[str, ...]
    omitted_control_key_names: tuple[str, ...]
    output_bytes: bytes = field(repr=False)


@dataclass(frozen=True, slots=True)
class StartupInputResult:
    source_sha256: str
    output_sha256: str
    target_mode: int
    artifact_relative_path: str
```

These are internal immutable values, not public configuration, GraphState, or
RunState fields. `output_bytes` must never appear in repr, exceptions, logs, or
audit artifacts.

## 6. Detection and canonicalization

The controller parses the already-pinned host clone as untrusted data using the
safe YAML loader and strict path helpers. It derives one plan before sandbox
creation and canonicalizes accepted assignments as sorted UTF-8
`KEY=VALUE\n` bytes. It records accepted, synthetic, and omitted-control key
names plus hashes, never values.

The root `.env` has two Compose semantics: it satisfies the service-level
`env_file`, and Compose also reads it for project interpolation. The design must
not describe it as inert. Before Boot, the controller renders Compose config in
the guest with the generated file and records a resolved-config hash. The render
must preserve the same Compose file set and service set; interpolation may only
populate existing scalar values. Any materialized repository-relative bind
source must resolve inside the verified clone. The rendered model must not add
another Compose file, privileged mode, host networking, a host/container-engine
socket, device mapping, or an external/escaping bind source. Existing source
declarations remain subject to the established sandbox and hardening semantics;
this check proves that materialization did not introduce a new one.

After provider clone verification and before any workload command, the
materializer repeats guest-side `stat`, `readlink`, `realpath`, size, UTF-8, and
SHA-256 checks through argv-only `SandboxProvider.exec()`. The guest source hash
must equal `StartupInputPlan.source_sha256`, the target must remain absent, and
the target parent must remain the verified guest clone root.

## 7. Guest-local exclusive creation

Because the provider has no host-to-guest copy operation, canonical bytes are
base64-encoded and passed as inert argv data to one code-owned fixed shell
adapter. The adapter body is constant, reviewed, and persisted by hash. It is
not generated by the model or target repository.

The adapter must:

- run before any untrusted workload process exists;
- use `umask 077` and shell noclobber/exclusive creation;
- reject an existing target or link;
- decode only the controller-produced bounded base64 payload;
- set mode `0600`;
- verify a regular non-linked target, exact mode, and expected SHA-256;
- emit only a bounded success/failure code, never file content.

The no-workload concurrency boundary plus pre/post path checks is required for
the shell adapter's safety argument. If the available guest utilities cannot
prove these properties, implementation stops; no provider-interface or host
fallback workaround is allowed.

## 8. Audit artifacts and collision handling

Each baseline/candidate attempt receives one exclusive
`startup-input-attempt-NNNN.jsonl` in its already-owned attempt directory. The
writer uses `O_CREAT | O_EXCL | O_NOFOLLOW`, mode `0600`, bounded writes, fsync,
and the repository's established collision-safe slot pattern.

The start/terminal records contain only:

- schema version, purpose, and sequence;
- source/target relative paths;
- source/output SHA-256;
- accepted, synthetic, and omitted-control key names;
- resolved Compose config SHA-256 and the fixed Compose-file identity;
- adapter SHA-256 and argv category, not payload argv;
- guest validation disposition, target mode, and bounded reason;
- monotonic elapsed time.

Values, base64 payloads, host absolute paths, credentials, and source file bytes
are prohibited from artifacts.

## 9. Baseline, retry, resume, and sandbox loss

Every `_boot` attempt creates a fresh sandbox today. The same immutable plan is
therefore verified and materialized immediately after each successful provider
create and before `boot_compose()`. The file remains available for Boot,
baseline Journeys, and baseline observation in that sandbox, then disappears
with sandbox destruction.

No checkpoint field is added. On resume, the controller deterministically
reconstructs the plan from the still-pinned host clone, verifies Compose/source
hashes, and compares any prior terminal audit record. A new sandbox always gets
a new exclusive attempt artifact and a newly verified file. If the host clone,
source hash, Compose identity, or prior audit identity differs, resume fails
closed. Loss of a sandbox never implies that the guest file still exists.

## 10. Candidate experiment parity

`run_experiment()` already creates a fresh candidate sandbox. The same generic
materializer must run after candidate provider create and before candidate
`boot_compose()`, using the same source/output and resolved-config hashes and
policy as baseline.
The overlay remains separate and immutable. Journeys, observations,
KEEP/ROLLBACK, and accepted Compose handling remain unchanged.

This can be implemented as one internal function called at the two existing
post-create/pre-Boot sites. It must not add a graph node, state machine,
watchdog, Provider, or public option.

## 11. Failure and cleanup semantics

Detection failure occurs before sandbox creation when possible. Any guest
validation or materialization failure occurs inside `managed_sandbox`, records
`UNSUPPORTED`, skips Boot, and relies on the existing forced destroy boundary.
Partially created guest state is never reused. The host clone is read-only and
must remain byte-for-byte unchanged. Cleanup and empty inventory remain required
for every real test and Linkding canary.

## 12. TDD and verification plan after approval

Implementation requires a separate plan and RED-first tests for:

- every committed RG2 corpus case, including reconstructed symlink, size/entry
  overflow, duplicate, invalid UTF-8, shell syntax, control key, secret value,
  target escape, and pre-existing target;
- deterministic canonical bytes, closed control-key omission, empty output,
  source/output hashes, and resolved Compose hash;
- the root `.env` dual role, interpolation confinement, and rejection of any
  materialization-induced Compose file/service/privilege/network/socket/device/
  escaping-bind change;
- no value in repr, logs, errors, or artifacts;
- exact adapter argv category/body hash, exclusive creation, mode `0600`,
  post-write hash, and failure cleanup;
- baseline retry and resume reconstruction without new checkpoint fields;
- candidate experiment parity before Boot;
- unchanged GraphState, RunState, API, CLI, report, Journey, and KEEP/ROLLBACK
  semantics;
- a trusted real-SBX fixture followed by one exact-SHA Linkding canary;
- Ruff, format, mypy, full pytest, branch coverage at least 85%, pre-commit,
  diff-check, and independent security/code review.

## 13. Authorization gate

No implementation plan, RED test for production behavior, or production edit is
authorized until the Owner explicitly selects Option A or Option B. If Option B
is selected, the approval must explicitly acknowledge that control-prefixed
assignments are omitted rather than causing whole-template rejection, while all
host-environment restrictions remain unchanged.
