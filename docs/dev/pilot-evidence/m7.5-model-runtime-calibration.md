actual `OpenAICompatibleModelAdapter` each terminated at the adapter's existing
10-second request timeout with the credential-free error
`ModelAdapterError: model request failed`.

One official native API prewarm was then allowed to complete:

- total elapsed: `78.871948 s`
- reported model-load duration: `51.8867753 s`

This proves a cold-start/request-timeout incompatibility. Repeated 10-second
requests cannot establish a warm model because each request cancels before the

## Engineering ruling

1. Do not add a new JSON-only or HTTP-500 fallback. The current official runtime
   accepts the exact Journey schema directly.
2. TDD the adapter request ceiling from 10 to 90 seconds while preserving the
   3-second connect timeout. This is an HTTP-operation timeout, not the total
   model-call wall-clock bound.
3. TDD the outer planner ceiling from 100 ms to 95 seconds so it bounds the
   complete adapter call, including an existing retry, while admitting the
   observed 78.872-second cold load.
4. Keep explicit cancellation and exception observation.
5. Add only the existing Journey tool/action/param/assertion matrix to the
   bounded prompt; do not change the DSL or deterministic verifiers.
6. After Task 4, a cold exact-schema call through the modified real adapter must
   complete inside the 95-second outer planner deadline and validate normally.
   The native 78.872-second prewarm supports selecting candidate bounds but does
   not itself prove cold exact-schema adapter support. Failure blocks the metric
   cohort.
7. Before the metric cohort, perform one trusted synthetic prewarm and freeze
   the runtime/model fingerprint to remove evaluation variance.
8. An explicit no-model control produced `journey_count=0` and recovery
   `stop / no recovery action`; no default request was synthesized.

### Public-path results and retained limitation

All three warm Recovery calls reached the production adapter through public
`propose_recovery()`. Each made one exact-schema request, received HTTP `200`,
and used no JSON-only fallback. The returned schema objects were rejected by
the existing recovery policy; the only retained public result was
`stop / unsafe proposal`. This is a model-assisted recovery usability
limitation, not a Task 4 frozen-gate failure and not a policy-valid result.
Changing the recovery prompt or production policy remains out of scope.

All three warm Journey calls reached the production adapter and materializer
through public `plan_journeys()`. Each made one exact-schema request, received
HTTP `200`, used no JSON-only fallback, and returned one policy-valid Journey.

The invalid loopback probe made exactly two requests: one through public
`propose_recovery()` and one through public `plan_journeys()`. Both received
HTTP `200`, used exact-schema mode without fallback, and failed closed under
the unchanged production policy.

Official unload returned HTTP `200` in `0.224790 s`. The following
`GET /api/ps` reported the exact model nonresident before cold planning began.
The immediate cold public `plan_journeys()` call then returned one policy-valid
Journey in `8.634944 s`, below the `95.0 s` outer deadline, with one HTTP `200`
exact-schema request and no fallback.

### Cancellation boundary ruling

The 95-second planner value is the outer model-planning ceiling. Cancellation
and exception observation therefore remain callback-based and do not synchronously
drain arbitrary adapter cleanup. Python cannot safely force-kill an in-process
coroutine that repeatedly suppresses `CancelledError`. The explicit trust
boundary is that `ModelAdapter.structured()` must eventually cooperate with
cancellation for zero lingering model tasks; a delayed cooperative adapter is
observed to completion, while a controlled non-cooperative regression proves
that planner return remains bounded and then releases the test task. No cleanup
grace, watchdog, thread, state machine, or public-interface change was added.

This calibration started no sandbox, ran no target Compose, and issued no SBX
daemon lifecycle command.
