## Pre-update evidence retained

On Ollama `0.20.7`:

- a simple strict-schema cold request completed in about `39.06 s`;
- a warm real `RecoveryAction` request completed in about `0.731 s`;
- the exact private RepoTrial Journey schema received HTTP `500` with an
  invalid-JSON-schema capability message;
- one manual JSON-only response passed transport validation but did not satisfy
  the existing Journey policy, and a later JSON-only response failed structured
  validation.

This evidence justified updating and recalibrating the official runtime. It does
not authorize a generic HTTP-500 fallback.

## Post-update probes

### Cold behavior

Before prewarming, three RecoveryAction and three Journey requests through the
actual `OpenAICompatibleModelAdapter` each terminated at the adapter's existing
10-second request timeout with the credential-free error
`ModelAdapterError: model request failed`.

One official native API prewarm was then allowed to complete:

- total elapsed: `78.871948 s`
- reported model-load duration: `51.8867753 s`
- terminal status: success
- response length retained: `2` characters; response content was not retained

This proves a cold-start/request-timeout incompatibility. Repeated 10-second
requests cannot establish a warm model because each request cancels before the
load completes.

### Warm exact-schema behavior

After prewarm, three requests per exact current schema passed through the real
adapter:

### Current planner and policy behavior

Using the current production prompt and code:

- `_journey_proposal_before_deadline()` returned its deadline sentinel in
  `0.100580 s`;
- direct transport of the same Journey prompt completed in `7.597908 s` and
  returned one schema-valid Journey proposal;
- existing Journey policy materialized `0` Journeys from that proposal;
- `propose_recovery()` returned `stop / model timeout` in `0.100515 s`.

The exact Journey schema therefore works on official Ollama `0.33.2`; the
remaining generic defects are the contradictory planner/adapter timeout bounds
and a prompt that does not describe the already-frozen Journey policy matrix
well enough for this 4B model.

## Engineering ruling

1. Do not add a new JSON-only or HTTP-500 fallback. The current official runtime
   accepts the exact Journey schema directly.
2. TDD the adapter request ceiling from 10 to 90 seconds while preserving the
   3-second connect timeout. This is an HTTP-operation timeout, not the total
   model-call wall-clock bound.
3. TDD the outer planner ceiling from 100 ms to 95 seconds so it bounds the
   complete adapter call, including an existing retry, while admitting the
   observed 78.872-second cold load.
4. Keep explicit cancellation and exception observation.
5. Add only the existing Journey tool/action/param/assertion matrix to the
   bounded prompt; do not change the DSL or deterministic verifiers.
6. After Task 4, a cold exact-schema call through the modified real adapter must
   complete inside the 95-second outer planner deadline and validate normally.
   The native 78.872-second prewarm supports selecting candidate bounds but does
   not itself prove cold exact-schema adapter support. Failure blocks the metric
   cohort.
7. Before the metric cohort, perform one trusted synthetic prewarm and freeze
   the runtime/model fingerprint to remove evaluation variance.
8. An explicit no-model control produced `journey_count=0` and recovery
   `stop / no recovery action`; no default request was synthesized.

This calibration started no sandbox, ran no target Compose, and issued no SBX
daemon lifecycle command.
